## Slide 1

Custom TaskOps — Hugo Ng. A personalized, extensible workflow that automates recurring checks and repairs while keeping validation consistent across creation, hardening, context extension, and review fixes. Current native Muse package; deck private to Hugo Ng.

## Slide 2

Entry points are the starting actions: create a task, harden it, extend context, or resolve review findings. All these modifications require common checks: oracle/setup correctness, specification clarity and test-spec alignment, and resistance to reward hacking. Custom TaskOps ties each entry into one shared verification and repair loop, so a single command invokes checks, applies blocking fixes, and rechecks instead of the author repeatedly prompting for manual verification and iteration. Every substantive edit invalidates prior evidence. The workflow repeats within its bounded retry budget, commits only when required gates pass, and reports unresolved blockers without committing. Official reviews supply current quality criteria; empirical gates apply when required.

## Slide 4

Compare three implemented entry skills, not hypothetical integration categories. Each has different inputs and edits, then uses one shared validation/commit loop.

create-task accepts an idea or invokes the proposal phase of ideate-task when no concrete idea is supplied, subject to current seed/authoring requirements. It scaffolds the detected track’s spec, tests, environment, verifier and reference solution. Prefer codimango task init when the current track/format supports it. Generate the README via the current official README skill, currently team-aai:update-readme, resolved at runtime. Creation measurements depend on task/track policy; the plugin does not claim that every new task always runs a five-trial calibration.

harden-task requires a valid existing task. failure-researcher returns a bounded brief from current-task and owned-task failure trajectories using the Codimango CLI. Establish the empirical five-trial baseline before edits. Use the evidence to change task difficulty, then run post-edit sanity and official independent review. Run five comparable candidate trials using supported local tooling (current TBench example: codimango bench run -p <task> -a <gate-agent> -m <gate-model> --k-to-n -k 5 --jobs-dir <scratch>/jobs --json). Commit only when the configured empirical target passes; lower but still out-of-range success counts are insufficient. Resolve live model/agent identities and track commands rather than hardcoding them.

quality-fix uses quality-issue-researcher to collect Codimango quality, rubric, validation, trial and human-review findings pinned to the current commit. Repair task-owned defects such as spec/test misalignment, oracle failures and verifier weaknesses; do not blindly apply stale findings or interpret infrastructure failures as difficulty. If repairs adopt hardening/easing policies, inherit their empirical baseline and post-edit gates under the same outer owner; otherwise ordinary repair does not automatically require difficulty trials.

Shared behavior: changed content must pass sanity and the current official track review, then all required operation measurements before one scoped commit. One outer operation owns edits, research handoffs, fixes, measurements and commit; official skills supply their maintained procedures and quality criteria. Pre-edit baselines do not consume the post-edit budget. Any failed sanity, review or failed/incomplete empirical batch consumes a validation attempt; the third failure stops uncommitted before more repairs. A successful third attempt may commit. Five trials form one measurement batch within an attempt. Runtime source discovery and explicit policy determine current capabilities. ## Slide 5

The three central pieces are skills, references, and profiles. Skills are Markdown instructions defining workflow steps and handoffs—not executable hook scripts. create-task combines research and scaffolding with the canonical validation and commit loop; harden-task and quality-fix reuse it. Use a skill to drive custom steps, invoke existing official skills, or combine both under one owner. References hold reusable shared policies: sanity, independent review, the shared three-validation-attempt ledger, research, measurement, and scoped commit. Edit the shared rule once rather than duplicating it in each entry skill. Profiles adapt that workflow per track: task layout, verifier/tool commands, official review routing, scratch paths, and difficulty/context procedures or targets. Current authoritative sources and explicit task policy override stale hints; do not bypass official requirements. The cross-track customization explanation is merged here rather than repeated on a separate slide. Configuration is editable Markdown, not an automatic settings hierarchy: entry skills explicitly load shared references, detect the profile, and read the task repo adapter.

Secondary components: agents define research roles that return compact evidence briefs to save main-agent context. The main agent retains edits and final commit. Task repo AGENTS.md is outside the plugin and supplies local commands, paths, missing capabilities, and default track. Hooks are event-triggered executable scripts registered in the manifest; this package’s Stop hook only offers fast advisory checks and does not orchestrate the workflow or enforce retry limits. The native Muse manifest registers capabilities. Copy/fork or start fresh, register skills and hooks, validate, and install privately. Example: muse plugins validate . --json; muse plugins install /path/to/your-plugin --scope user; muse plugins approve your-plugin. Check each track against a real task; manifest validation does not establish track support. Ask AI to edit a skill, shared policy, or one profile to suit your workflow. Other harnesses need their own packaging conventions.
